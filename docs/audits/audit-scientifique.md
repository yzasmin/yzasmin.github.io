# Audit scientifique du portfolio data

## Verdict d'ensemble

Le portfolio est nettement au-dessus de la moyenne d'un portfolio de sortie de master : la traçabilité des chiffres est réelle, j'ai reproduit à l'unité près les résultats clés de trois projets sur six à partir des données brutes.
La faiblesse n'est pas l'honnêteté, elle est remarquable, mais la **validité des raisonnements qui transforment un chiffre en conclusion** : trois affirmations publiées reposent sur un test qui ne teste pas ce qu'elles prétendent (rattrapage des communes, justification de la branche 114D, supériorité de la recherche hybride).
Deux projets portent une promesse d'ingénierie plus forte que ce que le code garantit (aucun test sur le consommateur qui porte la garantie d'idempotence, normalisation ajustée avant le découpage des plis).
Un point de sécurité est à traiter aujourd'hui : une clé d'API Anthropic vivante en clair sur le disque, hors du dépôt mais dans le dossier du projet 5.
Pour un poste de Data Analyst ou de Data Engineer junior, le dossier tient et se défend ; pour un poste de Data Scientist, il manque un modèle industrialisé, une métrique économique et de la donnée d'entreprise.

### CRIT-2. La preuve de concept du projet EMOTIC est statistiquement fausse, et c'est elle qui justifie tout le projet

La fiche et le poster annoncent « 654 paires sur 2 080 significatives (31,4 %, contre environ 5 % attendus par hasard) justifiaient la branche ». Trois défauts, tous vérifiables dans le code.

**Preuve 1, le dénominateur est faux.** Dans « projets-data\projet-fin-etudes\notebooks\01_preuve_de_concept_yolo.ipynb », cellule 13 :

```python
pval_matrix = np.ones((80, 26),  dtype=np.float32)
for obj_idx in range(80):
    obj_col = yolo_binary[:, obj_idx]
    if obj_col.sum() < 30:  # ignorer les objets trop rares
        continue
    for emo_idx in range(26):
        if emo_col.sum() < 30:
            continue
```

La matrice de p-valeurs est initialisée à 1, et les objets comme les émotions trop rares sont sautés. Les paires sautées gardent p = 1, donc comptent comme non significatives, mais restent dans le dénominateur 2 080. Le fichier « results\resultats_poster.json » écrit pourtant `"paires_testees": 2080`. Une partie de ces paires n'a jamais été testée. Le taux de 31,4 % et la comparaison à « 5 % attendus par hasard » portent sur des ensembles différents.

**Preuve 2, la correction pour tests multiples est calculée puis jetée.** Même cellule :

```python
alpha_bonf  = alpha / n_tests
n_signif    = (pval_matrix < alpha_bonf).sum()
n_signif_05 = (pval_matrix < 0.05).sum()
```

C'est `n_signif_05`, le décompte **non corrigé**, qui est publié (654). Le décompte corrigé `n_signif` n'est qu'imprimé à l'écran, et le notebook ne contient **aucune sortie enregistrée** (vérifié : 0 sortie sur l'ensemble des cellules). Le chiffre corrigé n'existe donc nulle part. Même défaut, aggravé, dans « 05_mapping_interpretabilite.ipynb », qui publie 1 235 / 2 080 (59,4 %) sans qu'aucun `alpha_bonf` ne soit calculé.

**Preuve 3, le test n'est pas celui qui est nommé.** Le code applique `scipy.stats.pointbiserialr(obj_col, emo_col)` à deux vecteurs **binaires** (présence d'objet, présence d'émotion). La corrélation point-bisériale est définie pour une variable binaire et une variable continue. Sur deux binaires, elle se réduit au coefficient phi, et la p-valeur de scipy repose sur une approximation en t qui se dégrade fortement quand les marges sont déséquilibrées, ce qui est exactement le cas ici (Pain, Embarrassment et Suffering sous 500 annotations sur 34 320).

**Correction.** Republier trois chiffres au lieu d'un : le nombre de paires **réellement testées** (celles qui passent le seuil de 30), le nombre significatif à p < 0,05 sur ce dénominateur, et le nombre significatif après Benjamini-Hochberg (Bonferroni est trop conservateur ici, et les tests ne sont pas indépendants). Remplacer `pointbiserialr` par un test du khi-deux ou un test exact de Fisher sur le tableau 2x2, plus honnête sur deux binaires, et publier phi comme taille d'effet. Ce recalcul ne demande que le notebook 01 et les annotations : c'est une demi-journée, et il transforme le point le plus attaquable du projet en point fort.

### CRIT-3. Le pipeline streaming perd des messages sans que rien ne le voie, et le composant qui porte sa promesse n'a aucun test

Le projet 4 met en avant « la livraison est au moins une fois, et c'est la contrainte d'unicité qui rend l'écriture idempotente ». J'ai vérifié : **l'ordre est bien correct**, « projets-data\data-engineer\src\velomagg\consumer.py » lignes 136 à 138, l'écriture PostgreSQL précède `consumer.commit(asynchronous=False)`. Ce point de conception est juste et bien défendu.

**Preuve 1, la perte en amont est invisible.** « src\velomagg\producer.py » lignes 93 et 104, et « src\velomagg\replay.py » lignes 71 et 72, appellent `producer.flush(30)` sans jamais lire la valeur de retour. Cette valeur est le nombre de messages **non livrés** à l'expiration du délai. Aucun `on_delivery` n'est enregistré sur les `producer.produce()` (lignes 83 et 91 de producer.py, ligne 68 de replay.py). Un message perdu entre le producteur et Redpanda n'apparaît dans aucun compteur : `messages_recus` est compté côté consommateur, donc un message jamais publié est indétectable. La fiche affiche « Messages invalides (schéma) : 0 » comme une preuve de qualité ; ce zéro ne dit rien des messages qui n'ont jamais atteint le bus.

**Preuve 2, le consommateur n'a aucun test.** Les 22 tests portent sur « tests\test_gbfs.py », « test_migrate.py » et « test_replay.py ». Aucun ne touche `consumer.py` : ni `write_batch`, ni la formule `duplicates = in_batch_dups + (len(unique) - inserted)`, ni l'ordre commit SQL puis commit d'offset, ni le comportement après une panne entre les deux. Le composant qui porte la seule garantie forte du projet est le seul qui ne soit pas testé.

**Preuve 3, le rejeu après panne n'est idempotent que sur une table.** `INSERT_STATUS` porte bien `ON CONFLICT (station_id, last_reported) DO NOTHING`. Mais `raw.rejected_messages` n'a aucune contrainte d'unicité (« migrations\V001__schema_brut.sql »), `raw.ingest_batches` insère une ligne d'audit à chaque passage, et `UPSERT_INFORMATION` réécrit `updated_at = clock_timestamp()` même à contenu identique. Après un crash entre les deux validations, les compteurs publiés sont surcomptés et `updated_at` ment sur la date du dernier changement réel.

**Correction.** Trois gestes, une demi-journée chacun. Lire le retour de `flush()` et lever si non nul, plus un `on_delivery` qui incrémente un compteur `messages_non_livres` exporté dans « results\synthese.json ». Écrire trois tests sur `consumer.py` avec une fausse connexion : un lot normal, un lot contenant un doublon, et un lot rejoué après simulation de crash, en vérifiant que le nombre de lignes en base ne bouge pas. Ajouter une clé métier unique sur `raw.ingest_batches` (par exemple l'intervalle d'offsets du lot) pour que le rejeu ne double pas les compteurs.

### CRIT-4. Fuite inter-plis dans le projet Kaggle : la normalisation est ajustée avant le découpage spatial

**Preuve.** Dans « projets-data\challenge-kaggle\yasmina\train.py », `_standardize_pair` est appelée aux lignes 396 et 397, à l'intérieur de `prepare_data` (définie ligne 368). `prepare_data` est appelée ligne 938. Les blocs spatiaux et les masques de plis ne sont construits qu'ensuite, lignes 948 et 949 :

```
396:    env_train, env_test = _standardize_pair(env_train_df.drop(...), env_test_df.drop(...))
938:    prepared = prepare_data(cache_dir / cache_name)
948:    groups = build_spatial_blocks(prepared.metadata_train, args.spatial_grid_size)
949:    fold_masks = build_fold_masks(groups, args.n_folds, args.seed)
```

Les médianes, moyennes et écarts-types qui normalisent les variables d'un pli de validation ont donc été calculés en incluant ce pli. Ce n'est pas une fuite d'étiquettes, c'est une fuite de statistiques, et elle affaiblit précisément ce que la validation spatiale cherche à mesurer : la généralisation à une zone jamais vue.

**Comparaison interne au même dépôt.** Le pipeline de Guilhem fait l'inverse et proprement : « Guilhem\scripts\train_pa.py » ligne 84 appelle `fit_normalizer(feature_store, split="pa_train", survey_ids=train_ids)` avec les identifiants du pli courant seulement. Le dépôt contient donc les deux pratiques côte à côte, ce qui est une occasion en or de démonstration en entretien, à condition de l'avoir vu.

**Preuve associée, le pré-entraînement Presence-Only n'est pas filtré géographiquement.** « yasmina\train_po_pretrain.py » charge l'intégralité des observations Presence-Only (fonction `prepare_po_data`), les utilise pour un pré-entraînement unique, puis injecte les mêmes poids dans les cinq plis. Rien n'exclut les points Presence-Only situés dans les blocs de validation. Je n'ai pas les données pour mesurer le recouvrement réel : c'est une fuite **possible par construction**, pas une fuite démontrée. Elle suffit à rendre optimiste le « environ 0,35 en validation spatiale interne » cité dans la fiche.

**Correction.** Déplacer l'appel à `_standardize_pair` dans la boucle sur les plis, en n'ajustant que sur le masque d'entraînement. Puis, avant le pré-entraînement, retirer les points Presence-Only dont le bloc de 1 degré appartient au pli de validation courant, et mesurer l'écart de score avec et sans ce filtre : ce delta est une réponse en entretien qui vaut plus que le score lui-même. Si le score de validation baisse, la fiche doit citer le nouveau chiffre.

## Constats majeurs

### MAJ-1. La conclusion sur le rattrapage des communes est adossée à un test qui ne peut pas l'établir (elle tient quand même, je l'ai vérifiée)

**Preuve du défaut.** « projets-data\data-analyst\scripts\construire_notebook.py » lignes 109 à 121 corrèlent `prix_m2_median_debut` (le prix médian de 2021) avec `evolution_prix_m2`, défini en SQL comme `prix_2025 / prix_2021 - 1`. Le prix de 2021 est donc présent **dans les deux variables**, au numérateur de l'une et au dénominateur de l'autre. C'est un couplage mathématique : le bruit d'échantillonnage sur la médiane 2021 produit à lui seul une corrélation négative, sans aucun rattrapage réel. Le test de permutation des lignes 119 et 120 mélange `y` et détruit ce couplage : il teste l'indépendance des deux variables, pas l'absence de rattrapage. La p-valeur de 0,0017 ne dit donc rien sur l'alternative que la fiche nomme elle-même (« la régression vers la moyenne produit le même signe »).

**Ce que j'ai fait.** J'ai rejoué la chaîne complète depuis « data-analyst\data\raw\dvf_34_*.csv.gz » avec ma propre implémentation, puis construit le test qui manque : séparer aléatoirement les ventes de 2021 de chaque commune en deux moitiés, estimer l'axe des abscisses sur la première moitié et le dénominateur de l'évolution sur la seconde. Le bruit devient indépendant des deux côtés et le couplage disparaît. Sur 200 tirages :

| Type        | rho publié (p2021, evo) | rho(p2025, evo) | rho split-sample, médiane sur 200 tirages |
| ----------- | ----------------------- | --------------- | ----------------------------------------- |
| Appartement | -0,652                  | -0,422          | **-0,612** [-0,716 ; -0,465]              |
| Maison      | -0,317                  | -0,079          | **-0,256** [-0,359 ; -0,133]              |

**Conclusion.** Le rattrapage est réel : les deux intervalles excluent zéro, et la corrélation avec le prix de 2025, qui devrait changer de signe sous pur artefact, reste négative pour les appartements. La conclusion publiée est juste, la preuve publiée ne l'est pas.

**Correction.** Remplacer, dans le notebook et dans la fiche, la p-valeur de permutation par la corrélation split-sample avec son intervalle. Une phrase suffit : « corrélation de rang -0,61 [-0,72 ; -0,47] pour les appartements, prix de départ et évolution estimés sur deux moitiés disjointes des ventes de 2021, ce qui exclut le couplage mathématique ». C'est plus court que la formulation actuelle et beaucoup plus solide.

### MAJ-2. Le gain de la recherche hybride n'est pas distinguable du bruit, et il est la métrique de tête de la fiche

**Preuve.** La fiche met en tuile « Rappel@10, recherche hybride 0,875 ». - Comparaison appariée (McNemar exact) hybride contre BM25 sur le rappel@10 : l'hybride gagne 2 questions, en perd 0, **p = 0,50**.
- Sur le rappel@1 : gagne 6, perd 3, **p = 0,51**.

L'écart entier entre 0,828 et 0,875 tient à deux questions sur trente-deux.

**Preuve du second défaut, la construction du jeu d'évaluation.** « src\re2020\evaluation.py » juge un passage pertinent s'il **contient littéralement** la chaîne `contient` déclarée dans « eval\questions.jsonl ». À la reprise du projet, écrire 20 questions supplémentaires à partir de cas d'usage réels et non des passages, et garder 10 questions de développement jamais utilisées pour publier.

### MAJ-3. La réserve sur l'autocorrélation du projet R cite le mauvais coefficient, et sous-vend le travail

**Preuve.** La fiche écrit : « L'agrégation hebdomadaire réduit l'autocorrélation sans l'annuler (0,54 en médiane) : les p-valeurs restent optimistes ». Le 0,54 est l'autocorrélation de rang 1 des **niveaux** des séries (j'ai recalculé la médiane sur « results\autocorrelation_lag1.csv » : 0,694 en journalier, 0,538 en hebdomadaire, sur 21 séries). Or pour un test **apparié**, la quantité pertinente est l'autocorrélation des **différences**, et le code la calcule déjà, ligne 278 de « projets-data\analyse-statistique\R\02_analyse.R » (`a1 <- acf1(diff)`), puis l'enregistre. Les valeurs réelles :

- Test 1 (NO2 semaine contre week-end), colonne `acf1_diff` de « results\test1_no2_semaine_weekend.csv » : de **-0,45 à -0,10** sur les 8 stations. Négative, donc l'effectif effectif est **supérieur** à n. Les p-valeurs du test 1 ne sont pas optimistes.
- Test 4 (Béziers contre Montpellier), « results\test4_no2_beziers_montpellier.csv » : `acf1_diff = 0,22`, n = 58. Effectif effectif 58 x (1 - 0,22) / (1 + 0,22) = **37**, facteur d'élargissement de l'intervalle 1,25. L'IC de Hodges-Lehmann publié [-30,6 ; -27,1] devient environ [-31,0 ; -26,6]. La conclusion ne bouge pas.

**Preuve du défaut qui reste, et il est ailleurs que là où la fiche le place.** Le test 3 (Friedman, 144 semaines) et surtout le test 2 (Kruskal-Wallis sur des semaines consécutives) traitent blocs et observations comme indépendants alors que les niveaux hebdomadaires sont autocorrélés.

- Test 3 : à effectif effectif 43 au lieu de 144, le khi-deux de 510,0 tombe vers 152 et la p-valeur de 4,6e-109 vers 1e-32. Conclusion inchangée, précision affichée fantaisiste. Un indice le confirme : la statistique V du post-hoc vaut 10 440 pour plusieurs paires, soit exactement 144 x 145 / 2, le **maximum arithmétique possible**. La p-valeur est un plancher numérique, pas une mesure d'évidence.
- Test 2 : c'est le cas le plus sérieux, et il n'est pas signalé. Les séries d'ozone sont les plus autocorrélées du jeu (0,64 à 0,78 en hebdomadaire), et Kruskal-Wallis ne bénéficie d'aucun appariement. L'effectif effectif tombe vers 23. Plus fondamentalement, sur trois ans il n'existe que **12 blocs saison-année réellement indépendants** : à cette échelle, la significativité du contraste été-hiver devient marginale. L'effet physique est certain, mais ce plan d'expérience ne contient que trois répétitions par saison, et c'est cela qu'il faut dire.

**Preuve du troisième défaut, l'attribution est inversée.** Le README du dépôt écrit que « les p-valeurs des tests **non appariés** restent optimistes ». Friedman est un test **par blocs** : il suppose l'indépendance des blocs, donc des semaines, et il est touché exactement comme Kruskal-Wallis. L'exonérer n'est justifié par rien, le code ne calcule jamais l'autocorrélation des rangs intra-bloc.

**Correction.** Remplacer la réserve actuelle par : « pour les tests appariés 1 et 4, l'autocorrélation des différences va de -0,45 à +0,22 : l'appariement absorbe la dépendance temporelle et les p-valeurs ne sont pas optimistes. Pour le test 3, l'autocorrélation hebdomadaire ramène l'effectif effectif de 144 à environ 43 : la conclusion tient, la p-valeur affichée non. Pour le test 2, le plan ne contient que 12 blocs saison-année indépendants : c'est la taille d'effet (epsilon carré au moins 0,527) qui porte la conclusion, pas la p-valeur. » Cette formulation est à la fois plus exigeante et plus flatteuse que celle d'aujourd'hui.

### MAJ-5. Une phrase du projet 6 tire une conclusion causale et lit une absence de preuve comme une preuve d'absence

**Preuve.** Le rapport conclut le test 1 par : « le trafic de fin de semaine ne suffit pas à faire respirer les axes majeurs ». Deux problèmes dans une phrase.

1. À Montpellier Liberté, p_holm = 0,107, mais l'estimation ponctuelle est une baisse de 5,3 %, écart de Hodges-Lehmann de 2,2 µg/m³, **IC95 [0,0 ; 4,4]** (colonnes `ic95_bas` et `ic95_haut` de « results\test1_no2_semaine_weekend.csv »). Cet intervalle est parfaitement compatible avec une baisse réelle allant jusqu'à 4,4 µg/m³. Dire « ne suffit pas » est une affirmation **sur l'effet** que les données ne portent pas.

## Points forts réels, à ne pas sous-vendre

1. **La traçabilité tient au recalcul indépendant, ce qui est rare.** J'ai réimplémenté la chaîne DVF depuis les cinq fichiers `.csv.gz` bruts, sans importer le code du dépôt, et j'obtiens **105 463 ventes exactement**, le même prix médian d'appartement 2025 (3 483,33 euros), les mêmes volumes (-30,9 % puis +13,4 %) et les mêmes médianes pour Sète, Montpellier et Béziers. J'ai recompté les 1 096 fichiers du flux E2 et obtenu **477 820 mesures exactement**. J'ai recalculé les trois taux du projet 4 depuis l'archive GBFS brute (0,1354 contre 0,1359 publié, écart dû aux instantanés en direct). C'est un argument d'entretien de premier ordre, et il est vérifiable en trois minutes devant l'interlocuteur.

2. **Les résultats décevants sont publiés.** 3,1 % de réponses dans le périmètre pour la génération locale. L'hybride qui perd trois points de rappel@3 face à BM25 seul. Montpellier Liberté non significatif alors que c'est l'axe le plus circulé. Le modèle EMOTIC 1,8 point sous le papier de référence. Le score de l'équipe sous la ligne de référence du challenge. Très peu de portfolios font cela, et cela vaut plus qu'un score flatteur.

3. **La validation spatiale du projet 2 est une vraie validation spatiale.** J'ai lu le code : `build_spatial_blocks` découpe en blocs de 1 degré et `build_fold_masks` répartit les **blocs**, pas les relevés. La calibration du nombre d'espèces est faite sur la validation hors échantillon et jamais sur le test. La réponse à « comment évitez-vous de surestimer votre score quand le test est ailleurs » est dans le code, pas dans le discours.

4. **Les conditions des tests statistiques sont réellement vérifiées avant le choix du test, et les tailles d'effet accompagnent systématiquement les p-valeurs.** Shapiro-Wilk, Levene, autocorrélation des différences, W de Kendall, epsilon carré, r de Wilcoxon, correction de Holm par famille. ## Trous de couverture métier

Les six projets couvrent bien **Data Analyst** (projets 3 et 6, plus deux ans d'alternance Power BI), correctement **Data Engineer** sur la partie streaming et modélisation (projet 4), et partiellement **Data Scientist** (projets 1 et 2, tous deux académiques).

Ce qui manque, par ordre de coût pour une candidature dans le bassin Montpellier et Béziers :

1. **Aucun modèle industrialisé.** Pas d'API d'inférence, pas de conteneur de service, pas de registre de modèles, pas de version de modèle suivie. Les deux projets de modélisation s'arrêtent au score. C'est le trou le plus visible pour un poste de Data Scientist.
2. **Aucun suivi en production.** Pas de détection de dérive, pas de réentraînement, pas de seuil d'alerte, pas de garde-fou de promotion. Le projet 4 a des tests de qualité de données, ce qui est le plus proche, mais l'ordonnanceur est une boucle `while` dans un script shell.
3. **Aucune orchestration.** Ni Airflow, ni Dagster, ni Prefect. dbt existe mais sans planificateur réel.
4. **Aucun cloud, aucun entrepôt.** Ni AWS, ni GCP, ni Azure, ni Snowflake, ni BigQuery, ni Databricks. C'est une exigence fréquente des offres data engineer locales, et le portfolio n'a rien à montrer.
5. **Aucun test A/B ni inférence causale.** Pas de plan d'expérience, pas de différence de différences, pas de score d'appariement, pas d'uplift. Le mot « corrélation » revient partout, le mot « effet causal » nulle part avec une méthode qui l'établirait.
6. **Aucune donnée massive.** Le plus gros volume est de 412 496 lignes traitées par DuckDB sur un poste, et 12 Go téléchargés puis filtrés à la volée. Aucun traitement distribué, aucun partitionnement à l'échelle, aucune notion de coût de calcul.
7. **Aucun modèle supervisé sur donnée d'entreprise avec une métrique économique.** Pas de churn, pas de scoring, pas de prévision de demande, pas d'euros gagnés ou perdus. L'alternance chez Angelotti contient pourtant exactement cela (l'outil qui repère les opérations à risque de marge) : c'est le projet manquant, et c'est le seul qui parlerait directement à un recruteur.
8. **Aucune prévision de série temporelle.** Le projet 6 décrit, le projet 4 observe, aucun ne prévoit. Deux des six projets manipulent pourtant des séries temporelles.

**Recommandation de priorité.** Un septième projet réglerait les trous 1, 2 et 7 d'un coup : reprendre le modèle de marge de l'alternance sur des données synthétiques ou publiques, l'entraîner avec une métrique en euros, le servir derrière une API conteneurisée, et ajouter une page de suivi de dérive. Deux semaines, et le portfolio devient complet sur les trois métiers.
